# Baton

> Рабочее название. Слово `baton` в нише агентной автоматизации уже занято несколькими проектами; окончательное имя ещё не выбрано (кандидат — `segue`).

Headless-раннер сценариев на YAML, в которых чередуются **детерминированные** шаги (скрипты, HTTP-вызовы) и **недетерминированные** (вызовы LLM, кодинг-агенты). Один бинарник, один прогон на вызов, никакого UI и сервера. Аналог n8n для команд, которые предпочитают хранить сценарии как YAML в git и запускать их из CI или cron.

## Зачем

Задачи вида *собрать данные скриптом → отдать модели на интерпретацию → разложить результат и опубликовать его* обычно решаются одним из двух плохих способов. Либо bash-обвязкой вокруг `claude -p` в каждом репозитории, которая не контролирует ни бюджет, ни безопасность, либо тяжёлой платформой с сервером, базой данных и веб-интерфейсом, что избыточно для одноразового прогона в CI.

Baton закрывает этот промежуток: сценарий — это файл в репозитории, прогон — одна команда, а всё состояние прогона — каталог на диске.

## Принципы

**Раннер детерминирован, агентность — это шаг.** Baton не является агентом. Он исполняет DAG шагов в предсказуемом порядке, и вся агентность инкапсулирована в шаге `agent:` (запуск CLI-агента) или в шаге `llm:` с инструментами (раннер сам ведёт tool-loop через API). Это делает прогоны воспроизводимыми, а бюджет — поддающимся жёсткому контролю.

**Интеграции живут снаружи бинарника.** Baton знает протоколы — HTTP, JSON, схемы авторизации, пагинацию, — но не сервисы. GitLab, GitHub, Jira, Telegram и другие описываются *API-паками*: YAML-файлами в отдельном репозитории, зафиксированными по версии и чексумме. Паки реализуют небольшие интерфейсы (`forge/v1`, `tracker/v1`, `notify/v1`), поэтому один сценарий ревью работает на GitLab, GitHub и Gitea при смене одного входного параметра. Новая интеграция — это новый файл, а не новый релиз.

**Модель никогда не видит креды.** Каждый авторизованный вызов внешнего API проходит через встроенный шлюз: агент получает узкие инструменты вида `gitlab.get_mr_changes(iid)`, а токены подставляет раннер. Публикация результатов — отдельный детерминированный шаг со своими правами доступа. Секреты — отдельный тип в системе значений, и попытка подставить секрет в промпт отклоняется на этапе валидации сценария.

**Способность вместо доступа.** Агенту не выдаётся ни `curl`, ни `bash`, ни доступ к сети. Вместо этого сценарий объявляет параметризованные команды (`test`, `lint`), которые становятся инструментами с валидируемыми аргументами и запускаются без shell.

**Структурный контракт между шагами.** Каждый LLM-шаг возвращает JSON по схеме. Ветвление допускается только по провалидированным полям, в идеале — по `enum`. Невалидный вывод модели — это отдельный класс ошибки со своей стратегией повтора.

**Fail-fast по умолчанию, уведомление всегда.** Падение любого шага роняет прогон, если явно не указано иное. Секция `on_failure` выполняется для любого класса ошибки, включая исчерпание бюджета.

**Триггеры снаружи.** Baton ничего не знает про расписания и вебхуки. Используйте cron, systemd timer или расписание вашей CI. Именно это отличает CLI-инструмент от платформы.

## Как выглядит сценарий

```yaml
version: 1
name: code-review
description: Review a merge request, depth chosen by risk

inputs:
  project: { type: string, required: true, pattern: '^[\w.-]+/[\w.-]+$' }
  mr:      { type: int,    required: true }
  base:    { type: string, default: origin/main }

defaults:
  engine: claude-code
  model: anthropic/claude-sonnet-4-6
  timeout: 10m

budget:
  usd: 8
  time: 40m

steps:
  - id: diff
    run:
      argv: ["git", "diff", "{{ .inputs.base }}...HEAD"]

  - id: classify
    llm:
      model: anthropic/claude-haiku-4-5
      prompt: prompts/classify.md
      with: { diff: "{{ .steps.diff.stdout }}" }
      schema: schemas/classify.json

  - id: review
    when: 'steps.classify.result.risk != "low"'
    agent:
      prompt: prompts/review.md
      with: { project: "{{ .inputs.project }}", iid: "{{ .inputs.mr }}" }
      profile: review
      max_turns: 25
      budget_usd: 2
      result: schemas/findings.json

  - id: publish
    http:
      op: forge.post_comment
      auth: forge_rw
      args:
        project: "{{ .inputs.project }}"
        iid: "{{ .inputs.mr }}"
        body: "{{ render \"templates/review.md.tmpl\" .steps.review }}"
    dedupe_key: "review-{{ .inputs.project }}-{{ .inputs.mr }}"

  - id: gate
    assert: 'len(filter(steps.review.result.findings, .severity == "blocker")) == 0'

on_failure:
  - notify: telegram
    message: "{{ .run.name }} failed: {{ .run.error.class }} at {{ .run.failed_step }}"
```

Агент в шаге `review` может читать репозиторий и вызывать read-only операции форжа. Он не может опубликовать комментарий — для этого есть шаг `publish` с write-кредом, который модель никогда не видит.

## Типы шагов

| Шаг | Назначение |
|---|---|
| `run` | Выполнение команды через argv без shell, с захватом stdout/stderr и кода выхода |
| `http` | Вызов операции API-пака (`forge.post_comment`) или сырой запрос, креды из хранилища секретов |
| `llm` | Один вызов модели через Anthropic, OpenAI, OpenRouter или любой OpenAI-совместимый API, с обязательной схемой результата, цепочкой запасных моделей и опциональными инструментами |
| `agent` | Запуск CLI-агента (Claude Code в v1) с навыками, инструментами и MCP-серверами |
| `foreach` | Параллельная обработка списка с ограничением степени параллелизма и контролем частичного успеха |
| `until` | Ограниченный цикл с условием выхода, например «править, пока не пройдут тесты» |
| `assert` | Намеренное падение прогона с отдельным кодом выхода, для блокировки merge в CI |

## Обзор возможностей

**Управление потоком.** Условия `when:` на expr-lang (типизированные, без побочных эффектов); `switch:`/`cases:` с проверкой полноты покрытия относительно `enum` схемы; `needs:` для явных зависимостей; статическая проверка ссылок — обращение к результату потенциально пропущенного шага без обработки `null` является ошибкой валидации.

**Инструменты агента.** Файловая система: чтение всегда доступно, запись только внутри workspace, deny-списки путей. Команды истории git и локальные коммиты, сетевые операции недоступны. Объявленные argv-команды с валидацией аргументов, таймаутами и лимитами вызовов. Read-only операции паков из аллоулиста, представленные как узкие инструменты, авторизуемые раннером. `fetch` для публичных URL по аллоулисту доменов. Сторонние MCP-серверы из аллоулиста, запускаемые раннером, инструменты с произвольными URL помечаются `unsafe`. `submit_result` как канал сдачи результата с валидацией по схеме. Межпрогонное хранилище `state` в области видимости сценария. Готовые профили разрешений: `review`, `fix`, `research`.

**Обработка ошибок.** Классифицированные ошибки — `transient`, `schema`, `command`, `timeout`, `budget`, `policy`, `config` — с retry, привязанным к классу; сбой `schema` повторяется с текстом ошибки валидации в контексте. `on_error: fail | continue | fallback`. Автоматический retry шагов с побочными эффектами запрещён без `dedupe_key`. Частичный успех в `foreach` при пороге `min_success`. `on_failure` на уровне прогона с каналами уведомлений из глобального конфига. Различимые коды выхода для успеха, ошибки выполнения, сработавшего assert, некорректной конфигурации, исчерпанного бюджета и прерывания.

**Прогоны, кеш, возобновление.** Каждый прогон — каталог `runs/<id>/`, хранящий состояние, артефакты, логи вызовов инструментов и стоимость. Результаты шагов кешируются по хешу определения шага и его входов, поэтому повторный прогон не платит за токены заново. `baton resume <id>` продолжает с упавшего шага. Каждый вызов инструмента агентом записывается в аудит-лог.

**Бюджеты и наблюдаемость.** Лимиты на шаг и на прогон по токенам, долларам, числу ходов агента и времени. Стоимость прогона фиксируется в состоянии и в уведомлениях. Структурированный лог событий JSONL с редактированием секретов во всех выводах.

## Области применения

- **Код-ревью в CI.** Джоба вызывает `baton run review.yaml -i mr=$CI_MERGE_REQUEST_IID`. Сценарий классифицирует изменение, выбирает глубину ревью, запускает read-only агента, публикует замечания отдельным шагом и блокирует merge при наличии блокеров. Один сценарий покрывает любой форж — специфичен только вызов.
- **Периодические отчёты.** Cron запускает сценарий, который обходит репозитории или системы, собирает данные скриптами, отдаёт их модели на обобщение и отправляет отчёт в Telegram, Slack или на почту. Падение одного источника не роняет отчёт, но фиксируется в нём.
- **Триаж и классификация.** Маршрутизация входящих тикетов или инцидентов: классификация по `enum`, диспетчеризация через `switch`, создание тикетов через `http`-шаги с write-кредами, которые модель не видит.
- **Автоматические исправления с проверкой.** Профиль `fix` позволяет агенту править workspace и запускать объявленные тестовые команды внутри ограниченного по числу итераций цикла `until`; результат — diff-артефакт, а его применение — отдельный шаг.
- **Регламентные проверки.** Детерминированные шаги собирают факты о зависимостях, лицензиях или конфигурации, LLM-шаг их интерпретирует, а `assert` останавливает пайплайн при нарушении.

## Чем Baton не является

- **Не платформа.** Нет веб-интерфейса, сервера, базы данных.
- **Не планировщик.** Нет встроенного cron или вебхуков (возможно позже, как `baton serve`).
- **Не агент.** Не решает, какие API вызывать — это делает сценарий.
- **Не замена CI.** Детерминированные сборки и тесты остаются в CI. Baton добавляет шаги, требующие интерпретации.

## Статус

**Запускается.** Сценарии из шагов `run`, `assert`, `http`, `llm`, `foreach` и `notify` исполняются целиком: `baton run`, `resume`, `runs`, `validate`, `schema`. [Пример недельного отчёта](../../examples/weekly-report.yaml) — текущий приёмочный сценарий: `foreach` по проектам через пак GitLab, дайджест от модели по JSON-схеме и уведомление, с кешем, так что повторный прогон той же недели не тратит токенов. Шаги `agent` тоже исполняются — движком `fake` и адаптером Claude Code: раннер готовит workspace, отдаёт `commands` шага как инструменты через шлюз MCP и берёт результат из `submit_result`. Инструментов файловой системы, git, api, fetch и state в шлюзе пока нет, поэтому агенту доступны только объявленные команды.

Дорожная карта по [техническому заданию](spec.md) (раздел 15):

| Веха | Содержание | Статус |

| M2 | Провайдеры (Anthropic, OpenAI, OpenAI-совместимые/OpenRouter), шаги `llm`, структурированный вывод, `foreach`, кеш, resume, `on_failure`, отчёты | готово |
| M3 | Движок `fake`, адаптер Claude Code, шлюз MCP, `submit_result`, `commands`, профили, аудит-лог | в работе |
| M3.5 | Паки из git с пинингом и чексуммами, реестр интерфейсов `forge/v1`/`tracker/v1`/`notify/v1`, команды `baton apis` | не начато |
| M4 | `until`, `fallback`, `dedupe_key`, `switch`, `fetch`, `state`, сторонние MCP, обработка сигналов | не начато |

## Сборка

Требуется Go 1.25 или новее.

```sh
make build      # собирает ./baton с метаданными версии
make test       # go test ./...
make race       # go test -race ./...
make all        # fmt, vet, test, build
```

## Запуск

```sh
baton validate examples/weekly-report.yaml
baton run examples/weekly-report.yaml \
    -i 'projects=["acme/web", "acme/api"]' -i since=2026-01-01
```

Провайдер, каналы уведомлений и таблица цен живут в глобальной конфигурации: `~/.config/baton/config.yaml` или `./baton.yaml`, либо там, куда указывает `--config`. Секреты читаются из окружения или из файлов в момент, когда они нужны шагу; они не попадают ни в каталог прогона, ни в кеш, ни в промпт модели.

Каждый прогон пишет `runs/<id>/` с `run.json`, `events.jsonl` и выводом каждого шага. Прочитать это обратно можно через `baton runs list`, `baton runs show <id>` и `baton runs logs <id>`, а `baton resume <id>` продолжает упавший прогон с упавшего шага. `--dry-run` печатает план, `--json` печатает события в JSONL, `--no-cache` игнорирует кеш шагов. `baton tools <scenario.yaml> --step ID` печатает инструменты, которые получит агент шага, ничего не выполняя.

## Технологии

Go, один статический бинарник. Зависимости: парсер YAML, expr-lang для выражений, gojq для трансформов в паках, валидатор JSON Schema, Go SDK для MCP, SDK провайдеров моделей (Anthropic, OpenAI, OpenAI-совместимые, включая OpenRouter). Никаких внешних сервисов, никакой базы данных. Интеграции с сервисами живут в отдельном репозитории паков.
