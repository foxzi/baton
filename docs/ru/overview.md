# Baton — описание проекта

> Имя закреплено: `baton`. Слово в нише агентной автоматизации используют и другие проекты, но бинарник, каталог конфига `~/.config/baton` и путь модуля `github.com/foxzi/baton` остаются такими же.

## Одной фразой

Baton — это headless-раннер сценариев на YAML, в которых чередуются детерминированные шаги (скрипты, HTTP-запросы) и недетерминированные шаги (вызовы LLM, запуск кодинг-агентов). Один бинарник, один прогон на вызов, никакого UI и сервера. Аналог n8n для команд, которые предпочитают YAML в git и запуск из CI или cron.

## Зачем

Задачи вида «собрать данные скриптом → отдать модели на интерпретацию → разложить результат и опубликовать» сегодня решаются одним из двух плохих способов: либо bash-обвязкой вокруг `claude -p` в каждом репозитории, либо тяжёлой платформой с сервером, базой и веб-интерфейсом. Первое не масштабируется и не контролирует ни бюджет, ни безопасность. Второе избыточно для одноразовых прогонов в CI.

Baton закрывает промежуток: сценарий — это файл в репозитории, запуск — одна команда, всё состояние прогона — каталог на диске.

## Ключевые принципы

**Без обязательного состояния между запусками.** Baton не требует переносить `state/` из одного запуска в следующий. При необходимости сохраняются результаты работы в файлах; эфемерная файловая система CI не является ограничением архитектуры.

**Раннер детерминирован, агент — шаг.** Baton не является агентом. Он исполняет DAG шагов в предсказуемом порядке, а «агентность» инкапсулирована в шаге `agent:` (запуск CLI-агента) или `llm:` с инструментами (раннер сам ведёт tool-loop через API). Это делает прогоны воспроизводимыми и позволяет жёстко ограничивать бюджет.

**Интеграции — снаружи бинарника.** Baton знает протокол (HTTP, JSON, схемы авторизации, пагинация), но не сервисы. GitLab, GitHub, Gitea, Jira, Telegram, Slack описываются API-паками — YAML-файлами, которые грузятся из каталога или из git с пином версии и чексуммой. Паки реализуют небольшие интерфейсы (`forge/v1`, `tracker/v1`, `notify/v1`), поэтому один сценарий ревью работает на GitLab, GitHub и Gitea со сменой одного входного параметра. Новая интеграция — новый файл, а не новый релиз.

`baton apis import` заводит новый пак из документа OpenAPI 3: пути, методы и параметры выбранных операций превращаются в операции пака, паттерны выводятся из типов схемы (enum, integer, boolean), а схема авторизации переносится из документа, если пак-формат умеет её выразить (`apiKey`, bearer, basic). Остальное — трансформы, описания, readonly и пагинация — оставляется в виде пометок TODO для автора, потому что сам документ не говорит, какие поля важны и как обходить постраничный список. `baton apis validate` замыкает цикл: команда разбирает пак и прогоняет каждый записанный ответ из `examples/<op>.json` через конверт и трансформ операции, поэтому сломанное jq-выражение находится в CI, а не на следующем реальном вызове. Операция, объявившая `implements`, проверяется по реестру интерфейсов: имена аргументов должны совпадать с теми, что назвал интерфейс, операция не может требовать аргумент, который интерфейс считает необязательным, а трансформированный пример должен подходить под схему результата интерфейса. Тот же контракт запись `apis` сценария объявляет через `interface: forge/v1` — тогда выбранный пак проверяется на наличие операций интерфейса при загрузке, и смена GitLab на Gitea одним входом падает сразу и понятно, а не на первом вызове. `baton apis call <scenario.yaml> <api>.<op> -a k=v` работает в обратную сторону и вызывает живой сервис через запись `apis` сценария — с тем же базовым URL, секретом и таймаутом, что взял бы прогон; значения, которые не строки, передаются как `-a k:=<json>`.

**Модель никогда не видит креды.** Все авторизованные вызовы внешних API проходят через встроенный шлюз: агент получает узкие инструменты вида `gitlab.get_mr_changes(iid)`, а токены подставляет раннер. Публикация результатов — отдельный детерминированный шаг с собственными правами. Секреты — отдельный тип в системе значений, и попытка подставить их в промпт отклоняется на этапе валидации сценария.

**Способность вместо доступа.** Агенту не выдаётся `curl`, `bash` или сеть. Вместо этого сценарий объявляет параметризованные команды (`test`, `lint`), которые становятся инструментами с валидируемыми аргументами и запускаются без shell.

**Структурный контракт между шагами.** Каждый LLM-шаг возвращает JSON по схеме. Ветвление допустимо только по провалидированным полям, лучше всего — по `enum`. Невалидный вывод модели — это отдельный класс ошибки со своей стратегией повтора.

**Fail-fast по умолчанию, уведомление всегда.** Падение любого шага роняет прогон, если явно не указано иное. Секция `on_failure` выполняется при любом классе ошибки, включая исчерпание бюджета.

**Триггеры снаружи.** Baton не знает про расписание и вебхуки. Расписание — cron, systemd timer или schedule в CI. Это то, что отличает CLI-инструмент от платформы.

## Возможности

### Типы шагов

| Шаг | Назначение |
|---|---|
| `run` | Выполнение команды или скрипта без shell (argv), с захватом stdout/stderr и кодом выхода |
| `http` | Вызов операции API-пака (`forge.post_comment`) или сырой HTTP-запрос, креды из хранилища секретов |
| `llm` | Один вызов модели через Anthropic, OpenAI, OpenRouter или любой OpenAI-совместимый API, с обязательной JSON-схемой результата, цепочкой запасных моделей и опциональными инструментами |
| `agent` | Запуск CLI-агента (Claude Code в v1) с навыками, инструментами и MCP-серверами |
| `foreach` | Параллельная обработка списка с контролем степени параллелизма и частичного успеха |
| `until` | Ограниченный цикл с условием выхода (например, «править, пока тесты не пройдут») |
| `file` | Чтение, запись, дополнение или перечисление файлов рабочей области (`read`, `write`, `append`, `glob`); пути и паттерны ограничены рабочей областью |
| `assert` | Намеренное падение прогона с отдельным кодом выхода для блокировки merge в CI |

### Управление потоком

- `when:` — условие на шаге, язык выражений expr-lang, типизированный и без побочных эффектов
- `switch:` / `cases:` — многовариантное ветвление, раскрываемое при загрузке в по шагу на случай с условием `when:`
- Статическая проверка ссылок: ссылка на результат шага, который может быть пропущен, без обработки `null` — ошибка валидации
- `needs:` — явные зависимости, если порядок объявления недостаточен

### Инструменты агента

- Файловая система: `fs.read`, `fs.glob`, `fs.grep`, `fs.write` для движка без собственных файловых инструментов; чтение всегда, запись только внутри workspace, deny-списки путей
- Движок `claude-code` пользуется своими встроенными файловыми инструментами: шлюз `fs.*` ему не отдаёт, а deny-списки и запрет `Bash`/`WebFetch`/`Task` уезжают в `settings.json` и `--disallowedTools` самого CLI
- Git: `status`, `log`, `diff`, `blame`, `show`, локальный `commit`; сетевые операции недоступны
- Команды: объявленные argv-команды с валидацией аргументов, таймаутами и лимитами вызовов
- API: только read-only операции паков из аллоулиста, как узкие инструменты, авторизованные раннером
- `fetch`: чтение публичных URL по аллоулисту доменов с лимитом размера
- MCP: сторонние серверы из аллоулиста, запускаются раннером; инструменты с произвольными URL помечаются `unsafe`
- `submit_result`: канал сдачи результата с валидацией по схеме внутри цикла агента
- `state`: хранилище между прогонами в области видимости сценария
- Профили: `review`, `fix`, `research` как готовые наборы разрешений

### Обработка ошибок

- Классификация: `transient`, `schema`, `command`, `timeout`, `budget`, `policy`, `config`
- Retry с привязкой к классу; `schema` повторяется с текстом ошибки в контексте
- `on_error`: `fail` (по умолчанию), `continue`, `fallback` на запасной шаг
- Запрет автоматического retry шагов с побочными эффектами без `dedupe_key`
- Частичный успех в `foreach` с порогом `min_success`
- `on_failure` на уровне прогона с каналами уведомлений из глобального конфига
- Различимые коды выхода: успех, ошибка выполнения, сработавший assert, ошибка конфигурации, исчерпан бюджет

### Прогоны, кеш, возобновление

- Каждый прогон — каталог `runs/<id>/` с состоянием, артефактами, логами инструментов и стоимостью
- Кеш результатов шагов по хешу определения и входов: повторный прогон не платит за токены
- `baton resume <id>` — продолжение с упавшего шага
- Аудит-лог каждого вызова инструмента агентом
- `baton tools <scenario.yaml> --step ID` — печать инструментов, которые получит агент шага, без выполнения

### Бюджеты и наблюдаемость

- Лимиты на шаг и на прогон: токены, доллары, число ходов агента, время
- Стоимость прогона в состоянии и в уведомлениях
- Структурированный лог событий (JSONL), редактирование секретов во всех выводах

## Области применения

**Код-ревью в CI.** Джоба в GitLab CI, GitHub Actions или Gitea вызывает `baton run review.yaml -i mr=$CI_MERGE_REQUEST_IID`. Сценарий классифицирует изменения, выбирает глубину ревью, запускает агента с доступом только на чтение, публикует замечания отдельным шагом и блокирует merge при наличии блокеров. Один сценарий — для всех форжей, форж-специфичен только вызов.

**Периодические отчёты.** Cron запускает сценарий, который обходит репозитории или системы, собирает данные скриптами, отдаёт модели на обобщение и отправляет отчёт в Telegram, Slack или на почту. Падение одного источника не роняет отчёт, но фиксируется в нём.

**Триаж и классификация.** Разбор входящих обращений, инцидентов, задач: классификация по `enum`, маршрутизация по `switch`, создание тикетов через `http`-шаги с write-кредами, которые модель не видит.

**Автоматические исправления с проверкой.** Профиль `fix`: агент правит код в workspace, запускает объявленные команды тестов, цикл `until` ограничен числом итераций, результат — diff-артефакт, применение — отдельный шаг.

**Регламентные проверки.** Аудит зависимостей, лицензий, конфигураций: детерминированные шаги собирают факты, LLM-шаг интерпретирует и формирует резюме, `assert` останавливает пайплайн при нарушениях.

## Чем Baton не является

- Не UI и не платформа: нет веб-интерфейса, сервера, базы данных
- Не планировщик: нет встроенного cron и вебхуков (возможно в будущем как `baton serve`)
- Не агент: не принимает решений о том, какие API вызывать; это делает сценарий
- Не замена CI: детерминированные сборки и тесты остаются в CI, Baton добавляет шаги, требующие интерпретации

## Технологии

Go, один статический бинарник. Зависимости: парсер YAML, expr-lang для выражений, gojq для трансформов в паках, валидатор JSON Schema, Go SDK для MCP, SDK провайдеров моделей (Anthropic, OpenAI, OpenAI-совместимые включая OpenRouter), рендерер Markdown для `md2html`/`md2text` и парсер OpenAPI для `baton apis import`. Никаких внешних сервисов и баз данных. Интеграции с сервисами — это паки, а не код: те, что идут с репозиторием, лежат в `apis/`.

## Статус

Техническое задание на первую версию — в отдельном документе ([spec.md](spec.md)), реализация идёт по его вехам. Работает: ядро, HTTP-слой с паками, провайдеры моделей и шаги `llm`, `foreach`, кеш, `resume`, уведомления, шаги `agent` со шлюзом MCP, профилями инструментов и проксированием сторонних MCP-серверов, реестр интерфейсов и команды `baton apis`, шаги `until` и `switch`. Осталось: паки сверх тех семи, что лежат в `apis/`, и две операции интерфейсов, которых ни один сервис из набора не отдаёт, — `post_review` у GitLab и `create_issue` у Jira. Текущее состояние по вехам — в [дорожной карте README](README.md#статус).
