# Вычитка ТЗ: расхождения и пробелы

Документ фиксирует результат сплошной вычитки `docs/ru/overview.md` и `docs/ru/spec.md` перед началом реализации. Каждый пункт — либо противоречие между документами, либо ссылка на неопределённое понятие внутри ТЗ. Пункты не переносились в сами документы, чтобы не расходиться с их авторской редакцией: правки вносятся по мере того, как соответствующий раздел попадает в работу.

Нумерация разделов ниже — по `docs/ru/spec.md`.

## Расхождения между overview и ТЗ

### 1. `switch` не входит в список типов шагов

`overview.md` и §1/§3.2 ТЗ перечисляют семь типов шагов. §3.2 формулирует правило: «ровно одно из полей `run`, `http`, `llm`, `agent`, `foreach`, `until`, `assert` должно присутствовать». При этом §3.10 вводит `switch`/`cases` как ключ уровня шага — сахар, раскрываемый при загрузке.

Валидатор обязан применять правило «ровно одно из» **до** раскрытия сахара, иначе шаг со `switch` его не пройдёт. Формулировку §3.2 нужно расширить, либо явно указать порядок: раскрытие `switch` предшествует проверке.

### 2. Поведение `on_failure` при `assert`

`overview.md`: «Секция `on_failure` выполняется при любом классе ошибки, включая исчерпание бюджета».
§9.3: «Не выполняется при коде 2 (`assert`)».

Формально противоречия нет — `assert` в §3.9 определён как намеренная остановка, а не класс ошибки. Но фраза overview читается как безусловная. В README формулировка уточнена.

### 3. Состав git-инструментов агента

`overview.md` обещает `log`, `diff`, `blame`, `show` и локальный `commit`.
§7.3 описывает только два флага: `git: { read: true, commit: false }`.

Какие именно подкоманды открывает `read: true`, нигде не зафиксировано. Список нужен явный: он определяет и поверхность инструментов, и проверку в §13 («агент не может вызвать инструмент, не объявленный для шага»).

## Пробелы внутри ТЗ

### 4. `budget_tokens` не объявлен в формате сценария

§8.3 (учёт стоимости): «если модели нет в `pricing` — … бюджет по долларам для такого шага не проверяется, проверяется только по токенам (`budget_tokens`)».

Поля `budget_tokens` нет ни в §3.1 (верхний уровень, `budget`), ни в §3.2 (общие поля шага), ни в `defaults`. Нужно либо добавить его в формат — на уровне шага и/или прогона, — либо убрать упоминание и признать, что при отсутствии модели в `pricing` бюджет шага не контролируется вовсе.

### 5. У шага `run` нет поля `readonly`

`readonly: true` для `run` определяет сразу два поведения:

- §9.4: шаг без `readonly: true` считается имеющим побочный эффект и не ретраится автоматически без `dedupe_key`;
- §10.3: кеш по умолчанию включён для «`run` с `readonly: true`».

Но в §3.3 (описание шага `run`) поля `readonly` нет. Оно фигурирует только у объявленных команд в §7.5. Поле нужно добавить в §3.3 с дефолтом `false`.

### 6. Класс `policy` ссылается на несуществующий `publish`

§9.1 в источниках класса `policy` перечисляет «`publish`-валидация». Понятия `publish` в ТЗ больше нет ни в одном разделе — это остаток прежней редакции, когда публикация результата, по-видимому, была отдельным типом шага. Сейчас её роль играет обычный `http`-шаг. Упоминание удалить.

### 7. Неверная перекрёстная ссылка на кеш

§3.2, комментарий к полю: `cache: true # см. 8.3`. Кеш описан в §10.3; §8.3 — про провайдеров LLM.

### 8. Два синтаксиса авторизации у `http`

§3.4: `auth: forge_rw` — имя секрета строкой.
§7.4.1: `auth: { secret: forge_ro }` — объект.

Нужно выбрать один и разрешить второй как сахар, зафиксировав это в JSON Schema.

### 9. Пример `until` не соответствует формату

§3.8: `condition: "iter.test.exit_code == 0"`, где `iter` — «результат прошлой итерации». Обращение `iter.test` подразумевает, что в `iter` лежат именованные подшаги, но тело `until` — это `step:` с одним шагом **без** `id` (как и в `foreach`). Либо пример должен читаться `iter.exit_code`, либо тело `until` должно допускать список шагов с идентификаторами. Второе меняет формат, первое — только пример.

### 10. `Engine` и `Provider` смешаны в дереве пакетов

§2 размещает `anthropic/` внутри `internal/engine` рядом с `claudecode/` и `fake/`. Но это два разных интерфейса: `Engine` (§8.1) запускает внешний CLI-агент, `Provider` (§8.3) делает вызов к API модели. У них разные контракты, разные реализации и разные наборы тестов.

Нужен отдельный `internal/provider` с реализациями `anthropic`, `openai`, `openai_compatible`. Соответственно правило доступа к секретам из §2 («секреты доступны только `secrets`, `httpx`, `gateway`, `notify` и `engine`») должно включать и `provider` — ключи провайдеров нужны именно ему.

### 11. Не определено, кто владеет состоянием `submit_result`

§7.6: `submit_result` валидируется **шлюзом**; при успехе шаг помечается завершённым, процесс агента получает сигнал на завершение.
§8.1: результат возвращается в `AgentResult.Submitted` / `AgentResult.Result`, то есть от **движка**.

Движок не может знать содержимое результата — вызов пришёл в шлюз по HTTP. Значит движку нужен доступ к состоянию сдачи, которое ведёт шлюз: либо через переданный ему хендл, либо результат должен собирать исполнитель шага, а не движок. Это единственная неявная связь между двумя пакетами, и её стоит зафиксировать в §8.1 до начала M3.

### 12. Суффикс resume ломает формат run-id

§10.1: `run-id` — `YYYYMMDD-HHMMSS-<4 hex>`.
§10.4: повторный прогон получает тот же `id` с суффиксом `-r1`, `-r2`.

Если формат валидируется регуляркой (а он должен, поскольку `run-id` переопределяется флагом `--run-id` и участвует в путях), регулярка должна допускать необязательный суффикс `-r<n>`.

### 13. `render` не покрыт проверками пути

§5.2 даёт шаблонам функцию `render(path, data)`. Путь берётся относительно файла сценария, но ограничение на выход за его пределы нигде не сформулировано, и чеклист §13 не содержит пункта про path traversal в `render` — только про аргументы команд и `fs`. Пункт стоит добавить: `render "../../etc/passwd"` должен отклоняться.

## Технические риски

### R1. Статическая проверка ссылок не даётся expr-lang бесплатно

§4 требует двух проверок, которые выглядят как работа компилятора выражений:

- правило 5: ссылка на несуществующий `steps.<id>` — ошибка;
- правило 6: ссылка на шаг с `when:` без обёртки `coalesce`/проверки на `null` — ошибка.

`expr.Compile` с `expr.Env(...)` действительно типизирует окружение, но поведение зависит от его вида: при **struct**-окружении неизвестное поле даёт ошибку компиляции, а при `map[string]any` неизвестные ключи получают тип `any` и молча возвращают `nil` в рантайме. Идентификаторы шагов в Baton заведомо динамические, то есть естественное представление контекста — именно map.

Следствие: обе проверки потребуют либо динамического построения типа окружения под конкретный сценарий, либо собственного обхода AST выражения с сопоставлением путей `steps.*` со списком объявленных шагов. Это отдельная заметная работа внутри M1, которая в оценке «2 недели» не выделена отдельным пунктом.

Синтаксис из §3.9 — `filter(steps.review.result.findings, .severity == 'blocker')` — проверен и корректен: в предикатах expr-lang доступ к полю через ведущую точку допустим, `#` не обязателен.

### R2. Deny-списки встроенных инструментов Claude Code

Открытый вопрос №2 ТЗ. Механизм из §8.2 — временный файл настроек с PreToolUse-хуком плюс сверка флагов с `claude --help` установленной версии — самая нестабильная часть проекта: она зависит от чужого релизного цикла и не имеет стабильного контракта. ТЗ уже предусматривает план Б (отдавать `fs` через шлюз и запретить встроенные `Read`/`Grep`); решение принимается по результату эксперимента в M3.

Установленная в окружении разработки версия — Claude Code 2.1.263.

### R3. Имя проекта

Открытый вопрос №1 предлагает решить вопрос имени к M5. Но имя входит в module path, имя бинарника, путь `~/.config/baton/`, префикс переменных окружения `BATON_*` и имя репозитория паков `baton-apis`. Переименование после M1 — это правки в сотнях мест плюс сломанная совместимость конфигов у первых пользователей.

Решение на момент инициализации репозитория: остаёмся на `baton`, module path — `github.com/foxzi/baton`. Вопрос считается открытым до M5, как и в ТЗ, но цена его переноса растёт с каждым этапом.
