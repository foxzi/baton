# slack

API-пак, который учит baton работать со Slack Web API. Это вторая реализация
`notify/v1` после `telegram` (собственный комментарий в заголовке
pack.yaml): сценарий отправляет сообщение через `send(target, text, format)`,
не зная, какой именно чат-сервис на другом конце.

| | |
|---|---|
| Пак | `slack`, версия 1 |
| API | Slack Web API |
| Интерфейс | `notify/v1` — `send` |
| Дополнительные операции | `auth_test` |
| Аутентификация | `bearer` — токен бота как `Authorization: Bearer ...` |
| Base URL | по умолчанию `https://slack.com/api` |
| Пагинация | отсутствует — каждая операция это один вызов |

## Подключение в сценарии

В этом репозитории пока нет ни одного сценария, который вызывает `slack`,
поэтому пример ниже построен только из собственных `config`, `auth` и
`params` пака — так же, как подключается пак `telegram` (раздел 7.4.1
спецификации):

```yaml
secrets:
  slack_bot: { from: env, key: SLACK_BOT_TOKEN }

apis:
  slack:
    pack: slack
    from: ../apis/
    auth: { secret: slack_bot }

steps:
  - id: alert
    http:
      op: slack.send
      args:
        target: "#deploys"
        text: "nightly-build failed: http on publish"
```

Имя слева (`slack`) — это то, как шаг обращается к паку: шаг выше вызывает
`slack.send` и получает форму результата, которую обещает интерфейс.

Поскольку пак реализует `notify/v1`, та же самая запись `apis` может
обслуживать канал `notify:` глобальной конфигурации вместо явного шага
`http` — тем же общим способом, каким это делает любой пак с `notify/v1`
(раздел 12 спецификации):

```yaml
# baton.yaml (глобальный конфиг)
apis:
  slack:
    pack: slack
    from: ./apis/
    auth: { secret: slack_bot }

notify:
  chat:
    api: slack                   # пак, реализующий notify/v1
    target: "#deploys"
```

```yaml
# сценарий
- id: report
  notify: chat
  message: "nightly-build failed: http on publish"
```

## Конфигурация

| Ключ | Обязателен | По умолчанию | Значение |
|---|---|---|---|
| `base_url` | нет | `https://slack.com/api` | Корень API |
| `auth.secret` | да | — | Токен бота (`xoxb-...`), уходит как `Authorization: Bearer <токен>` |

Токен читается из секрета только в момент вызова; в сам пак он никогда не
записывается, а редактор секретов маскирует его в логах так же, как и любое
другое значение аутентификации.

## Операции

### `send` — `POST /chat.postMessage`

Не только чтение. Реализует `notify/v1.send`. Тело уходит как JSON
(`encode: json`).

| Аргумент | Имя на проводе | Где | Шаблон / ограничение | По умолчанию | Обязателен |
|---|---|---|---|---|---|
| `target` | `channel` | body | `^([CDG][A-Z0-9]{4,}|[@#][\w.-]+)$` | — | да |
| `text` | `text` | body | до 40000 символов | — | да |
| `format` | `parse` | body | `^(none|full)$`, одно из `none`, `full` | — | нет |

`target` — это словарь `notify/v1`; Slack называет тот же аргумент
`channel` и принимает либо id канала/группы/DM, либо `#name`. У Slack нет
собственного словаря форматов, кроме того, как он разбирает текст сообщения
на ссылки и упоминания, — именно на это и отображается `format` из
`notify/v1`: `none` оставляет текст ровно таким, как отправлен, `full`
разбирает его так же, как разобрал бы обычное сообщение пользователя.

```json
{ "id": "1717000000.123456", "target": "C0123456789" }
```

(`id` — это временная метка сообщения Slack `.ts`, она же служит его id;
`target` — это `.channel` без изменений.)

### `auth_test` — `POST /auth.test`

Только чтение. Без `implements`; проверяет, что настроенный токен бота
действителен, не отправляя сообщение.

Аргументов нет.

```json
{ "id": ..., "team": ..., "user": ... }
```

(`id` — это `.user_id`; `team` и `user` — собственные поля верхнего уровня
Slack с теми же именами.)

## Ошибки и envelope

Slack отвечает HTTP 200 с `{"ok": false, "error": "channel_not_found"}` так
же охотно, как и настоящим успехом, и никогда не оборачивает поля успешного
вызова ни во что — они лежат на верхнем уровне тела (собственный
комментарий в pack.yaml). Поэтому в envelope нет `unwrap`, только проверка
ошибки:

```yaml
envelope:
  error_when: '.ok == false'
  error_message: .error
```

Без этого `.ts` отклонённого вызова transform прочитал бы как `null`,
вместо того чтобы завершить шаг с ошибкой, которую вернул сам Slack.

## Заметки

- Комментарий в заголовке pack.yaml описывает `slack` как вторую реализацию
  `notify/v1` после `telegram`, поэтому сценарий, написанный под
  `notify/v1`, может обращаться к любому из них, не меняя свои шаги.
- Токен бота — это Bearer-токен, поэтому `auth.kind` — это `bearer`, и не
  нужны ни `name`, ни плейсхолдер в пути, в отличие от `path`-аутентификации
  `telegram`.
- Аргументы `target` и `format` операции `send` — это словарь `notify/v1`;
  на проводе пак переименовывает их в собственные `channel` и `parse`
  Slack.

## Проверка после правок

```sh
baton apis validate apis/slack
```

Команда разбирает пак и прогоняет через transform записанный ответ из
`apis/slack/examples/`, сверяя результат `send` со схемой интерфейса
`notify/v1`. То же самое делает набор тестов на каждом коммите, поэтому
пример нужно держать в согласии с transform.
