# jira

API-пак, который учит baton работать с Jira Cloud REST API, не внося название
Jira в сам бинарник. Пак реализует три операции интерфейса `tracker/v1`,
поэтому сценарий, написанный под `tracker/v1`, запускается на Jira Cloud —
достаточно подключить этот пак.

| | |
|---|---|
| Пак | `jira`, версия 1 |
| API | Jira Cloud REST API |
| Интерфейс | `tracker/v1` — `get_issue`, `search`, `comment` |
| Дополнительные операции | нет |
| Аутентификация | `basic`, пользователь из config, токен — секрет |
| Base URL | нет значения по умолчанию, `base_url` обязателен |
| Пагинация | нет (см. `search` ниже) |

## Подключение в сценарии

```yaml
secrets:
  jira: { from: env, key: JIRA_TOKEN }

apis:
  tracker:
    pack: jira
    from: ../apis/
    config:
      base_url: "{{ .inputs.jira_url }}"
      user: "{{ .inputs.jira_user }}"
    auth: { secret: jira }

steps:
  - id: issue
    http:
      op: tracker.get_issue
      args: { key: "{{ .inputs.key }}" }
```

Имя слева (`tracker`) — это то, как шаги обращаются к паку, поэтому один и
тот же сценарий вызывает `tracker.get_issue` независимо от того, с каким
трекером он работает. Сценарий может также объявить `interface: tracker/v1`
— тогда baton откажется загружать пак, который покрывает интерфейс не
полностью.

## Конфигурация

| Ключ | Обязателен | По умолчанию | Значение |
|---|---|---|---|
| `base_url` | да | — | Сайт Jira Cloud, `https://<site>.atlassian.net`; пути этого пака уже несут свой префикс `/rest/api/...` |
| `user` | да | — | Email аккаунта Atlassian, на который выпущен API-токен |
| `auth.secret` | да | — | Сам API-токен, уходит как половина пароля в HTTP Basic |

Jira Cloud принимает API-токен только через HTTP Basic: email аккаунта как
пользователь, токен как пароль. Bearer-токен — это концепция OAuth 2.0, и
Jira Cloud отклоняет API-токен, отправленный таким образом.

Jira Cloud одновременно предлагает два поколения REST API: v3 говорит на
Atlassian Document Format для форматированного текста, v2 по-прежнему
принимает и отдаёт обычный текст для тех же ресурсов. Этот пак держится v2
везде, где отправляет или читает текстовое поле, поэтому transform никогда
не должен обходить дерево документа ADF, и обращается к v3 только для
поиска, который v2 больше не обслуживает вообще.

## Операции

### `get_issue` — `GET /rest/api/2/issue/{key}`

Только чтение. Реализует `tracker/v1.get_issue`.

| Аргумент | Где | Шаблон | Примечания |
|---|---|---|---|
| `key` | path | `^[A-Z][A-Z0-9_]*-\d+$` | Ключ задачи, например `PROJ-123` |

```json
{ "key": "PROJ-123", "title": "Fix login button alignment on mobile",
  "status": "In Progress", "body": "The login button overlaps the password field...",
  "author": "Alice Johnson", "url": "https://example.atlassian.net/rest/api/2/issue/10002" }
```

Jira не отдаёт браузерную ссылку, только `self` — REST-адрес задачи;
сценарий, которому нужна кликабельная ссылка, собирает её сам из адреса
сайта и ключа.

### `search` — `GET /rest/api/3/search/jql`

Только чтение. Реализует `tracker/v1.search`.

| Аргумент | Где | Имя на проводе | Шаблон | По умолчанию | Обязателен |
|---|---|---|---|---|---|
| `query` | query | `jql` | `^[\s\S]+$`, максимум 4000 символов | — | да |
| `limit` | query | `maxResults` | `^\d+$` | — | нет |
| `fields` | query | `fields` | `^[\w,.-]+$` | `summary,status` | да (есть значение по умолчанию) |

```json
[ { "key": "PROJ-123", "title": "Fix login button alignment on mobile",
    "status": "In Progress", "url": "https://example.atlassian.net/rest/api/2/issue/10002" } ]
```

Старый `/rest/api/2/search` был выведен из эксплуатации и теперь отвечает
410 Gone; этот эндпоинт v3 — единственный поиск, который ещё обслуживает
Jira Cloud. Он листается через непрозрачный `nextPageToken`, а не через
offset, и эта версия пака его не обходит: сценарий получает только первую
страницу, размером `limit` (имя на проводе — `maxResults`). `fields`
запрашивается явно и по умолчанию равен `summary,status`, потому что без
него Jira отвечает меньшим набором полей по умолчанию, в котором нет
статуса.

### `comment` — `POST /rest/api/2/issue/{key}/comment`

Запись. Реализует `tracker/v1.comment`. Тело уходит как JSON.

| Аргумент | Где | Шаблон / ограничение | Примечания |
|---|---|---|---|
| `key` | path | `^[A-Z][A-Z0-9_]*-\d+$` | |
| `body` | body | 32000 символов | Текст комментария, обычный текст |

```json
{ "id": "10001", "url": "https://example.atlassian.net/rest/api/2/issue/10002/comment/10001" }
```

Операция не помечена `readonly`, поэтому её результат никогда не берётся из
кеша, а `--dry-run` её не отправляет.

## Чего здесь нет и почему

`create_issue` в этом паке выразить нельзя. Jira вкладывает поля новой
задачи в единый объект `"fields"` в теле запроса,
`{ "fields": { "project": { "key": ... }, "summary": ..., ... } }`, тогда как
пак умеет отправлять аргументы тела только плоско, на верхнем уровне.
Поэтому `tracker/v1.create_issue` невозможно выразить в текущем формате
пака; сценарий, которому нужно создать задачу в Jira, отправляет её сырым
http-шагом.

## Проверка после правок

```sh
baton apis validate apis/jira
```

Команда разбирает пак и прогоняет через transform каждый записанный ответ из
`apis/jira/examples/`, сверяя результат со схемой интерфейса для каждой
операции с `implements`. То же самое делает набор тестов на каждом коммите,
поэтому пример для операции с `implements` нужно держать в согласии с её
transform.
